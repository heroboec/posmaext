# Parallel requests Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Запускать загрузки товаров с секундным интервалом между стартами, а проверки Social Check — параллельно без искусственной задержки.

**Architecture:** Разделить очередь запуска HTTP и ожидание ответа. Изменения компактного состояния worker остаются последовательными, сетевые запросы выполняются вне блокировки; ответы объединяются с актуальным пакетом, а не перезаписывают его устаревшей копией.

**Tech Stack:** Существующие JS MV3, IndexedDB, node:test/jsdom/fake-indexeddb, без новых зависимостей.

**Spec:** Согласование в чате: товары стартуют в 0/1/2 секунды независимо от ответов; отмена запрещает дальнейшие старты. Social Check отправляет весь выбранный пакет параллельно, сохраняя идемпотентность и Retry-After. Пользователь подтвердил «да, делай».

## Global Constraints
- Первые 10 видимых заявок фиксированы, порядок стартов сохраняется, пропуски не заменяются.
- Интервал товаров: минимум 1000 мс между стартами либо больший интервал настройки; старые действия админки не изменять.
- Не сохранять полные строки товаров; не выполнять реальные/платные запросы при тестах.
- Нет автоматических новых платных повторов; те же ключи при неопределённом POST.
- Не менять соседний Social Check. Пользователь отдельно разрешил публикацию после тестов.

## Review Focus
- Медленный первый ответ не блокирует второй старт; ответы вне порядка привязаны к своим заявкам.
- Отмена/закрытие запрещают отложенные старты и сохранение сырых ответов.
- Параллельные ответы и синхронизация DOM не затирают результаты соседнего задания.
- Изменение магазина и удаление пакета во время запроса не приводят к пересылке в другой магазин/воскрешению пакета.
- Ошибка одного запроса не теряет уже отправленные результаты; 429 сохраняет паузу для последующих попыток.
